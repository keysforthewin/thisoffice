# 20 Questions — design

Date: 2026-07-26

## Summary

An optional, opt-in game layered on top of the office. When enabled, a randomly
chosen employee (or the boss, or Kat Person) asks the player a yes/no question
trying to guess the word the player is thinking of. A speech bubble appears above
the asker with YES and NO buttons. Each answer is recorded and immediately drives
the next question, generated by Claude Haiku from the accumulated question/answer
history. Once enough ground has been covered the asker starts making outright
guesses; a YES on a guess wins the round. The winner is photographed in situ —
a live screenshot of the current scene, framed on them with colleagues visible —
and that photo hangs on the wall behind the boss under an "Employee of the Month"
title until the next winner replaces it. Win counts per employee appear on the
wall TV's stats rotation.

The game is **off by default** and makes **zero LLM calls while disabled**.

## Goals

- A persistent, resumable game: the round survives a server restart and a page reload.
- Turn-based and player-paced — nothing happens until the player answers.
- Cost-transparent: the settings panel states what enabling it costs.
- No regression to the rendering-performance invariants documented in `CLAUDE.md`.

## Non-goals

- The server never learns the secret word. There is no answer validation beyond
  the player's own YES/NO clicks.
- No multi-player or per-viewer game state. One office, one round, shared by
  every connected client.
- No history of past winners beyond the current photo and the win tallies.

## Decisions taken

| Decision | Choice | Rationale |
|---|---|---|
| LLM transport | `claude -p --no-session-persistence --model claude-haiku-4-5` | No API key needed (`~/.claude` is already mounted in Docker); billed against the user's Claude plan. Reinstates the feedback-loop guard that left with the deleted `summarizer.ts`. Latency (~2–5 s) is irrelevant for a turn-based game. |
| Photo location | A **new** wall frame, separate from the existing painting | Reusing the painting frame would destroy the user's uploaded artwork on every win. |
| Screenshot | Client-side WebGL canvas capture with a camera fly-in | The browser already renders the scene. No headless-browser dependency, no second GL context. |
| Win condition | YES on a question Haiku marked as a final guess | Hard rules: must guess from Q15; office concedes at Q20. |
| Win tallies | `gameWins` on `UsageStats` | The TV already receives the whole `stats` object and `tvPages()` gates pages on non-empty values, so the new page needs no new plumbing. |
| Round reset | ~15 s celebration pause after the photo is hung | Lets the room admire the photo before the next question appears. |

## Architecture

```
┌─ server ─────────────────────────────────────────────────────────┐
│  quiz.ts        state machine + data/quiz.json persistence       │
│  quizPrompt.ts  (pure) prompt assembly + reply parse/repair      │
│  haiku.ts       the only process spawn: claude -p …              │
│  decor.ts       + eotmPath()/clearEotm()                         │
│  index.ts       + /api/quiz, /api/quiz/answer, /api/decor/eotm   │
└────────────────────────────┬─────────────────────────────────────┘
                             │  { type: 'quiz', quiz, capture? }
┌─ web ───────────────────────▼────────────────────────────────────┐
│  store.ts            quiz slice via applyServerMsg               │
│  quiz/SpeechBubble    drei <Html> bubble + YES/NO buttons        │
│  quiz/photoShot.ts    (pure) camera framing for the group shot   │
│  quiz/capture.ts      render → toDataURL → POST                  │
│  scene/EotmFrame      the wall photo + caption band              │
│  scene/tvContent.ts   + "Quiz champion" page                     │
│  settings/            + 20 Questions section (checkbox + cost)   │
└──────────────────────────────────────────────────────────────────┘
```

### Why a new `ServerMsg` type rather than a field on `OfficeState`

Quiz state changes on every question and every answer. Folding it into
`OfficeState` would rebroadcast the entire office state on each tick, and
`store.ts`'s `stableLayout` reference-carry-forward — which is what lets
`React.memo` on `Desk`/`Person` actually fire — only helps for the `layout`
subtree. A dedicated `{ type: 'quiz' }` message keeps the quiz off that path
entirely.

## Data model

Added to `shared/types.ts`:

```ts
/** One resolved question in the current round. */
export interface QuizAnswer {
  question: string;
  answer: 'yes' | 'no';
  /** true when the asker was making an outright guess rather than narrowing */
  guess: boolean;
  askerName: string;
  at: string;
}

/** The live speech bubble. Absent when the office is thinking or the game is off. */
export interface QuizQuestion {
  /** answers must echo this; guards against two tabs answering one bubble */
  id: string;
  text: string;
  guess: boolean;
  /** 'boss' | 'catPerson' | an employee id */
  asker: string;
  askerName: string;
  at: string;
}

export interface QuizWinner {
  name: string;
  variant: string;
  at: string;
}

/** Photo hanging in the Employee of the Month frame. Absent = empty frame. */
export interface EotmPhoto {
  /** capture timestamp; doubles as the cache-buster on /api/decor/eotm */
  v: number;
  name: string;
}

export interface QuizState {
  enabled: boolean;
  /** bumped each round; clients use it to drop stale bubbles */
  roundId: string;
  askedCount: number;
  answers: QuizAnswer[];
  question: QuizQuestion | null;
  /** true while the server is waiting on a client to deliver the win photo */
  awaitingPhoto: boolean;
  winner: QuizWinner | null;
  photo?: EotmPhoto;
}
```

`ServerMsg` gains:

```ts
| { type: 'quiz'; quiz: QuizState; capture?: QuizWinner }
```

`capture` is set **only** on the message sent to the single designated client
(see below). `UsageStats` gains `gameWins: Record<string, number>` keyed by
employee name. `OfficeLayout.wallItems` gains an `eotm` key so the new frame is
draggable in build mode.

### Persistence

`data/quiz.json` holds the whole `QuizState` minus `awaitingPhoto` (ephemeral).
The path is a constructor parameter, injected in tests exactly as
`Office`'s `dataFile` is — the existing invariant that tests never touch real
data files applies unchanged.

The photo itself lands in `data/decor/eotm.png` alongside `wallart.*` (both
gitignored). Only the metadata rides `QuizState`.

## Round lifecycle

```
enabled=false ──(PUT /api/quiz {enabled:true})──▶ askNext()
                                                     │
                          ┌──────────────────────────▼───────────────┐
                          │ pick asker → haiku → question broadcast  │
                          └──────────────────────────┬───────────────┘
                                                     │
              POST /api/quiz/answer {id, answer} ────┤
                                                     │
                     ┌───────────────────────────────┴────────────┐
             guess && yes                                    otherwise
                     │                                            │
                     ▼                                            ▼
        winner set, awaitingPhoto=true                        askNext()
        capture request → one client                     (concede at Q20:
                     │                                    status line, new round)
                     ▼
        POST /api/decor/eotm  (or 20 s timeout)
                     │
                     ▼
        photo hung · pushStatus('🏆 …') · gameWins[name]++
                     │
                     ▼
              15 s pause → new round (roundId bumped, answers cleared)
```

### Asker selection

Candidate pool: `'boss'`, every employee id, and `'catPerson'` when Kat Person
is present in the layout. Idle employees are preferred over working ones; the
boss and Kat Person are always eligible. Chosen uniformly at random from the
preferred set, falling back to the full set.

The bubble is independent of monitor content, so a working employee can ask
without disturbing their screen stream.

### Question generation

`quizPrompt.ts` builds a compact prompt: the numbered Q/A history, the count so
far, and the rules. It asks for a single JSON object `{ "question": "...",
"guess": true|false }`.

Rules enforced in the prompt **and** validated server-side:

- ≤ 12 words, phrased so YES or NO is a complete answer.
- Do not repeat a question already asked this round.
- From Q15 onward the question **must** be an outright guess (`guess: true`);
  the server overrides the flag if Haiku claims otherwise at that point.
- At Q20 the office concedes: a `⚠` status line, no further question, new round.

Parsing is defensive: extract the first `{…}` span, `JSON.parse`, coerce/trim,
cap length. Any failure falls through to the canned-question fallback below.

### The screenshot

The capture is **assigned, not elected**: the server tags `capture` onto the
quiz message it sends to a single socket (first in `wss.clients` insertion
order). Twelve open tabs therefore produce one photo, with no client-side
coordination. `capture` is never included in the state sent on a new connection —
a client that connects mid-window is not asked to shoot, and if the assigned
client disappears the photo timeout below covers it.

That client:

1. Resolves the winner's world position from the roster/layout.
2. `photoShot.ts` (pure, unit-tested) returns `{ position, lookAt, fov }` framing
   the winner off-centre with colleagues and the room behind them, clamped to stay
   inside the room walls.
3. `CameraRig` enters a `photo` mode: lerp in ~1.2 s, hold ~0.4 s.
4. `capture.ts` calls `gl.render(scene, camera)` and then
   `gl.domElement.toDataURL('image/png')` **in the same tick**. This is the
   reason not to set `preserveDrawingBuffer: true` on the `Canvas` — that flag
   would tax every frame forever for one screenshot per game.
5. POSTs the raw PNG bytes to `/api/decor/eotm?ext=png` (raw body, matching the
   existing wall-art and character upload routes — there is no multipart parser
   server-side and none is wanted).
6. Camera lerps back to whatever mode it was in.

## HTTP API

| Method | Path | Body | Notes |
|---|---|---|---|
| `PUT` | `/api/quiz` | `{ enabled: boolean }` | Enabling kicks off the first question. Disabling clears the pending bubble and stops all Haiku calls; round state is preserved. |
| `POST` | `/api/quiz/answer` | `{ id, answer: 'yes' \| 'no' }` | `409` on an id mismatch (stale bubble). Records the answer, then wins or asks again. |
| `POST` | `/api/decor/eotm` | raw PNG | Only accepted while `awaitingPhoto`; otherwise `409`. No `ext` parameter — a canvas capture is always PNG, unlike the user-uploaded painting. |
| `GET` | `/api/decor/eotm` | — | Streams the photo, `immutable` cache with `v` as the buster. `404` when absent. |

`DELETE /api/layout` additionally clears the EOTM photo, since it is a wall
hanging like the painting.

## Failure handling

Every path keeps the game moving; nothing leaves a dead bubble on screen.

| Failure | Behaviour |
|---|---|
| `claude` CLI missing, non-zero exit, or times out (30 s) | A canned narrowing question is used instead, and a `⚠ Haiku unavailable` status line is pushed. Round continues. |
| Haiku reply unparseable or empty after repair | Same canned fallback. |
| Haiku repeats a question already asked | Server detects the duplicate and uses the canned fallback rather than re-prompting (bounded work per turn). |
| No client connected, or capture fails / times out (20 s) | Winner is still crowned: status line and `gameWins` increment both happen. The **previous** photo stays up. A win is never lost to a closed tab. |
| Uploaded photo exceeds the size cap | `400`; treated as a capture failure per the row above. |
| Two tabs answer the same bubble | Second answer `409`s on the id check. |
| Game disabled mid-round | Pending bubble cleared, zero further calls. Re-enabling resumes from the recorded answers. |
| Server restart mid-round | `data/quiz.json` restores answers and `roundId`. `awaitingPhoto` is not persisted, so a restart during the photo window falls into the "capture failed" path. |

## Cost

One Haiku 4.5 call per answered question, with a prompt on the order of a few
hundred tokens (the Q/A history plus rules) and a one-line reply. A 20-question
round is therefore ~20 small calls. Nothing is called while the checkbox is off.

The settings panel states this explicitly next to the checkbox, so the game
cannot be enabled unknowingly.

## `CLAUDE.md` amendment

`CLAUDE.md` currently asserts *"No speech bubbles by design — all activity
renders on monitors."* This feature deliberately introduces one. The invariant
is amended rather than left contradicting the code: activity telemetry still
renders exclusively on monitors; the quiz bubble is game UI and is the single
documented exception.

## Known trade-off: win tallies key on name

`gameWins` is keyed by employee name, so a rehired `Dana` inherits her earlier
wins — desirable, since the roster already remembers per-seat name and variant
across eviction. The cost is that two distinct employees who both drew `Dana`
from the 32-name hire pool would merge totals. Accepted: the alternative is a
stable per-seat identity surviving eviction, which is more machinery than a
leaderboard warrants.

## Test plan

All new pure modules are unit-tested with vitest; the Haiku call is an injected
function so no test spawns a process.

**Server**

- `quizPrompt.test.ts` — prompt includes the full Q/A history; the forced-guess
  instruction appears from Q15; reply parsing handles clean JSON, JSON wrapped in
  prose, trailing commentary, missing `guess` field, over-long questions, and
  garbage.
- `quiz.test.ts` — first question on enable; answers recorded in order; a `yes`
  on a non-guess asks again; a `yes` on a guess sets the winner and
  `awaitingPhoto`; a `no` on a guess continues; `guess` forced from Q15;
  concession at Q20 bumps `roundId` and clears answers; stale answer id
  rejected; disabled state makes `askNext` a no-op and clears the bubble;
  `askFn` rejection falls back to the canned question and pushes a `⚠` status;
  photo timeout still crowns the winner; persistence round-trips through an
  injected data file.
- `stats.test.ts` — `recordGameWin` increments and persists `gameWins`.

**Web**

- `photoShot.test.ts` — the winner is inside the frustum, the camera is inside
  the room walls, and the shot is stable for winners at each seat including
  corner seats.
- `tvContent.test.ts` — a champion page appears once `gameWins` is non-empty,
  is absent when empty, and reports the top name with a total.
- `store.test.ts` — a `quiz` message populates the slice; a message for a
  superseded `roundId` does not resurrect an old bubble.
- `eotmTexture.test.ts` — caption band and photo framing math, mirroring the
  existing `wallArtTexture.test.ts`.

Manual verification (per the `run` skill): enable the checkbox, answer a few
questions, force a win, and confirm the photo hangs with the right caption and
the TV page appears.
